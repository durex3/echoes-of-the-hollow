# 开发—测试—验收流程

## 每个功能的完整循环

1. **定义任务**：复制 `docs/templates/task.md`，填写玩家触发条件、预期行为、不包含的内容、验收证据。
2. **识别影响**：列出场景/配置/存档是否改变；阅读相关 skill、本项目 AGENTS.md 及 [开发经验与防回归规则](development_lessons.md)。先核对用户最新约定，区分表现、碰撞和玩法规则，再确定实现范围。
3. **先验证风险**：新移动机制先在独立试验场测高度、距离、时间；失败则调整，不先铺大量关卡。
4. **实现**：分支 `feat/<topic>` / `fix/<topic>`；场景组合、类型标注、资源数据、事件通信。
5. **自动检查**：执行 `tools/check.ps1`。规范、导入、行为、存档进程检查全部通过。
6. **图形与试玩**：改动画/镜头/UI/地图时运行 `tools/check.ps1 -Visual` 并查看截图；按 testing.md 记录人工验收项。当前按用户要求继续内容开发，不等待逐轮试玩或提前制作试玩包；未试玩项保留待验收，在内容完成后的完整通关阶段集中执行。
7. **同步文档**：按影响更新架构、玩法、存档契约、操作说明、任务状态与 CHANGELOG。填写实际结果，不把计划当完成。
8. **检查差异与提交**：运行 `git diff --check`，确认无缓存、个人存档、外部素材原包；一个提交表达一个可回退的改变。

## 完成定义（DoD）

- [ ] 用户触发条件下行为正确；异常、重复输入、死亡/切房等边界已考虑。
- [ ] 不依赖本机绝对素材路径；新增依赖、Autoload、全局状态有理由。
- [ ] 默认检查全部通过，日志没有 SCRIPT ERROR / ERROR / FAIL。
- [ ] 与修改相关的自动测试真实检查结果，不只检查函数存在。
- [ ] 视觉修改检查实际渲染；玩法手感完成一次人工试玩。
- [ ] 存档变更有版本和迁移测试；测试不得写玩家正式存档。
- [ ] 对应文档/变更记录更新；已知限制写清楚。

自动检查通过代表自动门禁完成；未做人工试玩时必须记录待验收，不能宣称最终手感已获认可。
开发任务可在实现、自动检查、图形复核及文档齐备后提交，并明确标记人工验收待办；不能因此宣称发布验收完成。平台打包不属于每个功能的完成条件。

## Bug 流程

记录：引擎版本、复现步骤、实际/预期、日志、存档是否影响、截图。
优先级：P0 无法启动/数据丢失 → P1 主线阻塞/崩溃 → P2 操作/表现问题 → P3 打磨。
先复现与定位，再做最小修复；可重复的逻辑 bug 补回归用例；运行相关测试后再执行统一门禁。

## 分支和版本

默认 `main` 保持可运行。小任务短分支、小提交；提交格式 `feat(player): ...`、`fix(save): ...`、`docs: ...`、`test(world): ...`。
0.x 表示开发里程碑。增加新功能升次版本；兼容修复升补丁版本。修改版本时同步 project.godot、README、CHANGELOG。
发布标签只在对应验收和发布包测试完成后创建。本工程目前只初始化本地仓库，不自动推送或公开素材。

## 发布流程

锁定范围 → 全量门禁 → 从新游戏走到终点 → 旧档兼容 → 对照素材来源核对授权 → 安装同版本导出模板 → 导出 Windows → 在导出程序重走启动/战斗/存档/继续 → 记录版本和已知问题。
首次发布不将编辑器内运行通过等同于导出程序通过。`export_presets.cfg` 提供 Windows 预设；尚未进行正式导出验收。
当前发布顺序为：完成游戏内容 → 完整通关与打磨 → Windows 独立包验收 → 浏览器适配和目标浏览器验证。移动端未纳入当前任务；不因已有 Compatibility 渲染器就声称 Web 已兼容。

## 远程自动化

`.github/workflows/check.yml` 提供将来推送到 GitHub 后的门禁：固定 Godot 版本，校验官方下载摘要，运行与本地相同的无窗口检查，保存日志。
当前未配置远程仓库、未触发远程 CI；本地检查已经执行。视觉与真实设备验收仍由本机执行。
